# P0260 — code-level UI/NPC modularity audit (source checkpoint)

Date: 2026-10-18. **Authority:** GitHub `main` `669ec77da4a2bc9c880e878425cbf784aa33b05a` (P0259 verified pushed). D-035, D-046, D-047 are the accepted product/pipeline boundaries. **Classification: SOURCE AUDIT ONLY; no new WoW runtime test, capability authorization or Lua change.** Companion: `P0260_ALL_NPC_INTERACTION_ATLAS.md`.

## Question and result

Which already working Logres elements may be reused across ALL NPC interaction families without a broad rewrite, and where are display, source, action, ownership and camera concerns still coupled?

**Result: PARTIALLY MODULAR.** RewardModel/RewardVisual establish a real preview/live model-renderer separation, quest ContextVisual is a reusable render utility, and Logres has a common theme and module lifecycle. Most quest dialogue/paging/decision logic and camera interaction policy are not organized into cross-service components. No general NPC session coordinator, gossip option list UI, service catalog, price/transaction model, or bank/auction service module is present in the 56 tracked addon Lua modules at this commit. Their absence is a source finding, not an assertion that the game lacks those NPC services.

## Critical camera/session finding

`Core/State.lua` records generic `activeInteractionType` through `PLAYER_INTERACTION_MANAGER_FRAME_SHOW/HIDE`; it resets on `PLAYER_ENTERING_WORLD`. It does **not** represent an end-to-end NPC visit. `Camera/ProfileContexts.lua` separately iterates named native windows (including `GossipFrame`, `QuestFrame`, `MerchantFrame`, `ClassTrainerFrame`, `BankFrame`, `AuctionHouseFrame`, `PetStableFrame`, `WardrobeFrame`) and excludes `FlightMapFrame`; it also requires ordinary `UnitExists("npc")`. `Camera/WorldCombat.lua` listens to these lifecycle events and additional `MERCHANT_*`, `TRAINER_*`, `BANKFRAME_*`, `QUEST_*`, `AUCTION_HOUSE_*`, stable and other events; it assigns an interaction camera context below taxi/teleport/AFK/gathering priority. **Its `CheckCoexistence()` explicitly relinquishes Logres camera ownership when DynamicCam is loaded.**

Consequently, "Logres already detects NPC windows" is **not** equivalent to "Logres has a unified session orchestrator" or "Logres directly integrates DynamicCam transitions." A future NPC coordinator must not manipulate native/protected frame visibility merely to force camera behavior. **The user explicitly requires that currently working camera behavior not change. P0260 and the subsequent modularity extractions must leave all existing `Logres/Camera/*.lua` files, their event wiring, zoom behavior, camera profiles, DynamicCam coexistence, and interaction-transition policies unchanged.** The only permissible work at this stage is source documentation and, later, non-camera models/components that do not drive camera state. No new DynamicCam profile export is needed.

## Data and interaction separation: observed vs intended

- **Observed / source present:** `Quest/Dialogue.lua` guarded quest readers; `RewardModel.FromLive` and `Preview`; `RewardVisual:Present`; offer `TriggerProductionAction`; completion `Control:Gate/Activate/Restore/Click`; native offer suppression snapshot; `InteractionProbe` gossip read probes. Preview controls are synthetic and do not prove live selection.
- **Missing source abstractions:** common `NPCSession` lifecycle, `NPCPresentationModel`, reusable generic option-list renderer, service catalog/price model, selection/highlight/confirmation state, and source-specific live adapters for merchant/trainer/taxi/bank/auction. Nothing in the current files justifies implementing those transactions already.
- **Known safety boundary:** reward choices >0 or quest cost/eligibility ambiguity block Logres completion replacement. Native controls remain usable. `CompletionControl:Click()` restores native alpha/mouse targets **before** native completion dispatch; reported sub-second Blizzard window flash remains OPEN, not solved by modularity.
- **Game knowledge limit:** service NPC types in the atlas are *coverage requirements*, not claims that every Forever 1.60.1 NPC supports every modern WoW flow. Ability to draw a service screen is not capability proof of native APIs or transaction safety.

## D-046 preview-first coverage gap (project-wide)

The registered P tab includes 28 controls out of 96 developer-panel actions (source `Core/Commands.lua`). Preview controls cover reward single/multi, quest dialogue, health presets, some aura cases, XP/progress, active quest and compass art. Missing *full state matrices* include quest offer non-final/final, progress/Continue, reward empty/overflow/multiple choices with selected state, generic gossip options, merchant catalog/costs, trainer lists, travel, auction/bank shells, target/cast/pet/secure states, and fallback/restore visual scenarios. See `P0256_UNIVERSAL_PREVIEW_GALLERY.md`. A preview button is not a proof of data/model/render parity unless it renders the real component and uses inert actions.

## Ordered modularity extraction candidates (NOT approved code patches)

1. **N1 — contracts before Lua:** define small plain `NarrativeModel` and action descriptor schema with explicit `source`, `previewOnly`, page data, objective/footers and eligibility/fallback. Preserve existing accepted quest UI, page control and narrative source. Static checker for one model consumed by same render path. Full P-tab fixtures for 1-page, page1/final, long text, disabled/fallback, empty data. No native suppression/claim changes.
2. **N2 — narrative/view extraction:** isolate the existing bounded narrative/page visual from `Quest/Dialogue.lua`, retaining the existing feature as its first caller. In-client comparison of identical title, wrapping, footer, next/prev and accepted button positions; avoid duplicating the `+64` geometry/creating new native buttons.
3. **N3 — decision/control *presentation* extraction:** reuse accepted Accept/Decline/Complete art and positioning for inert generic decision fixtures. Action invocation remains owned by `OfferActionProbe` and `CompletionControl`, not the visual component. Do not confuse `CompleteQuest()` transition with final `GetQuestReward()`.
4. **N4 — plain option-list/catalog components:** only after a second real use case demonstrates need (generic gossip first); include list overflow, disabled options and costs, then a separate merchant/trainer fixture. No merchant transaction writes or unsupported native styling.
5. **N5 — documentation-only NPC session/lifecycle contract:** map existing state/event observations during gossip→quest→service→close and define a future optional **non-camera** coordinator interface. Do not implement camera reconciliation, change event subscriptions, call camera APIs, add polling, or modify `Logres/Camera/*.lua`. Any future camera change would require separate user approval and focused regression evidence.
6. **N6 — guarded integration tiers:** preserve native-backed/hybrid/full ownership choice per service. Capability-gate each service and prove fail-open behavior before suppressing any Blizzard information/control region.

N2-N6 are contingent on their preceding evidence, not a monolithic refactor. **Exact next item after P0260 push verification: N1 small plain narrative/action model contract and deterministic P-tab fixture inventory, or a narrower diagnostic if the existing panel binding blocks that contract.** No early bank/auction implementation.

## Required regression and exit gates for future fixes

- Clean static checker suite; model/view parity checker on generated candidate before tracked write; `git diff --check`; no frozen version pins in checkers.
- WoW preview side-by-side with accepted native quest/narrative/reward layouts; page1/final and visual choice/selection variants.
- No new Lua, taint, protected, secret-value or combat-lockdown error; restore usable stock before removing any Logres replacement action. No testing that consumes reserved quest 237.
- **Frozen camera regression:** no changed `Logres/Camera/*.lua`, no new dependency from the camera subsystem to extracted NPC components, and no changed framing/zoom transition policy. Existing camera tests remain applicable; no extra WoW camera manipulation is required for this audit. Environmental non-reproduction is DEFERRED, not PASS.
- Decline to auto-implement bank/auction/complex service transactions; run the D-047 post-modularity feasibility ranking **after** extraction proves actual reuse. Player benefit, camera continuity and native safety are explicit ranking factors.

## Negative findings and scope limits (retain)

- **NOT YET MODULAR:** feature-specific pagination/action layout remains in `Quest/Dialogue.lua`; multiple old attempts to copy/position Complete Quest failed visually before in-panel geometry was corrected. Do not duplicate view construction again.
- **NOT A CAMERA HANDOFF CONTRACT:** separate event, frame and generic interaction signals exist without confirmed priority for rapid service transitions. Proposing an observer is design, not runtime acceptance.
- **NOT A COMPLETE CATALOG:** `RewardVisual` displays six slots at most and no choice interaction, `InteractionProbe` truncates diagnostics at four rows; both require explicit overflow/safety design before merchant/bank reuse.
- **OPEN / DEFERRED:** native completion frame flash, selectable claim, 20-minute gameplay bug details, Live Progress/Continue, untested service interactions, other missing previews, optional QuestieDB coverage, complex bank/auction feasibility. Source audit cannot close these.
