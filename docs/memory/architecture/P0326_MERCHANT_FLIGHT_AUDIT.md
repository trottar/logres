## Narrow question and result

Can Logres reuse its existing NPC source/model/renderer/session architecture for merchant and flight-master interactions without replacing Blizzard's item transactions, fares, travel or camera? **Source-level answer: presentation and service/session vocabulary can be reused selectively; native service identity, safe data adapters, full content/interaction parity and actual frame/restoration gates are unproven.** The supported first integration tier is native-owned service controls with carefully gated Logres additions, not custom merchant purchases or flight execution.

## Merchant — proposed guarded source and UI capability checklist

**Read-only discovery first.** In the native merchant visit verify actual service identity (rather than infer from generic interaction or an assumed frame), native root existence and safely observable non-secret metadata. Differentiate merchant browse, single/multiple item stacks, unavailable/limited stock, buyback, repair and price/eligibility states. Only record data types and source availability if actually ordinary and supported; never pass potentially secret fields through string formatters or compare them for convenience. Source hints in the element index are NOT direct API contracts. The Blizzard merchant remains visible and clickable throughout this investigation; no purchase, sell, buyback or repair is invoked by diagnostics.

**Model/presentation only after proof.** A synthetic `merchant` catalogue/empty/unsupported fixture can use shared NPC visual tokens, but an eventual live adapter must use the identical renderer, explicit source identity and separate controller. Quantity, gold, stack-limit, stock, buyback, repairs, transactions and close controls stay native unless later independently proven. No new Blizzard-frame repositioning/parking without proving restoration first.

## Flight master — proposed guarded source and UI capability checklist

**Resolve native root and lifecycle first.** P0269 family policy mentions `FlightMapFrame`; P0270 capability probe inventories **both** `FlightMapFrame` and `TaxiFrame`; the P0279 element index uses `TaxiFrame` and Classic-named children. This disagreement reflects *candidate UI generations*, not confirmed coexistence or preference. In Forever inspect on-demand read-only candidate availability, lazy-loaded addon state, normalized interaction lifecycle and preservation of stock route map controls, without native geometry/children inspection simply to establish ownership.

**Keep travel native.** Never synthesize route nodes, unlocked state, fare, destination identity, connectivity or payment. No `TakeTaxiNode`/C_TaxiMap flight request or camera trigger from Logres preview. A synthetic read-only `flight available/unknown/no-source` presentation may be prepared once source contracts are established; even then Blizzard's entire route map, fare display, selection, close and travel stay usable.

## Existing diagnostics and November 4 acceptance plan

The registered developer panel in `Logres/Core/Commands.lua` contains **H — Native Service Frame Audit** (`/logres nativeframeaudit`) and **H — Native NPC Services Check** (`/logres nativeservicepolicycheck`). They are on-demand **READ-ONLY** inspections; no visible UI mutation is expected. With a *naturally available* merchant or flight-master open, record their output, which native root is present and whether the stock transaction/map, close and gossip handoff remain accessible. Check open/close, immersion OFF/ON only where safe, and stock restoration on natural exit. Merchant purchases/repair spending and actual flights are not required merely for diagnostic proof. Capture any Lua, taint, secret or protected error as a real failure.

**Do not start with H — Native Auto Position (TEST)** or any parking toggle to obtain this audit. Those are mutations and can require independent safety verification. P0321 **H — Gossip Stock Status (READ-ONLY)** and **Gossip Stock Toggle** must first be validated in Forever before treating its native parking as accepted.
