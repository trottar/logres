# 2026-09-30 — Project inception and memory bootstrap

## Context

Project Logres was defined as an immersive, world-first UI/HUD addon for World of Warcraft Forever.

The project deliberately adopts a repository-native external memory architecture so future work can resume from Git state rather than relying on conversational memory.

## Product direction established

Initial accepted direction includes:
- screen-edge health vignette instead of a conventional player health bar;
- compact resource percentage;
- no cast bars, with a possible minimal cast-confirmation glyph;
- enemy level hidden;
- restrained percentage target information;
- subtle relative-danger text/color treatment;
- no explicit elite warning by default;
- similar restrained ally/pet presentation;
- action controls as square/rectangular clusters;
- Immersion Mode as coordinated state;
- world compass as part of immersion and automatically absent in instances;
- PvP flag as an immersion modifier;
- Quiet/social immersion mode;
- later immersive questing/XP treatment;
- later integration of the user's DynamicCam behavior.

## Naming

The project name **Logres** was selected as an Arthurian/Camelot-adjacent homage appropriate to the WoW Forever/Classic+ context without using `Camelot` directly.

## Development environment

Canonical environment:
- Windows 11;
- WSL for development;
- repository in WSL Linux filesystem;
- WoW runs on Windows;
- deployment mechanism to be designed later.

## Git boundary

The user explicitly retains responsibility for commits and pushes.

## Memory architecture

The memory design is modeled on a detailed repository-native system:
- `CURRENT.md` for resumable state;
- `MEMORY.md` for durable facts;
- `LEARNINGS.md`;
- maintenance rules;
- design principles;
- architecture;
- decisions;
- investigations;
- evidence;
- handoff;
- patch records;
- roadmap state;
- dated chronology.

## Failure policy

The user explicitly required failures to be recorded because they are how the project learns.

This became a formal operating requirement:
- negative results are evidence;
- failed/rejected/rolled-back paths remain in history;
- retry conditions are stated;
- later success does not erase earlier failure;
- absence of a failure record must not be used to imply a clean result.

## Current position

Phase 0 begins with the memory bootstrap. The next technical task after that checkpoint is a WoW Forever API capability audit before implementation.


## I-001 source audit pass

After the memory bootstrap was pushed (`353c5b0`), Phase 0 moved to the Forever API capability audit.

Source/documentation findings:
- maintained DynamicCam Forever support records that Blizzard `WOW_PROJECT_ID` still answers MAINLINE on Forever;
- current maintained TOC evidence uses Forever interface `16001`;
- modern secret-value APIs are present on Forever;
- health/power can likely be displayed through native curves and secret-capable widget aspects without Lua reading the values;
- target level/classification are documented available;
- cast data is secret-restricted for non-player units;
- secure actions remain combat-lockdown constrained;
- player map position and facing are unavailable in instances;
- quest waypoint, PvP flag, instance, chat restriction, and camera APIs are present.

No source-pass result was promoted to runtime validation.

A temporary diagnostic addon, `tools/probes/LogresAPIAudit`, was prepared to collect sanitized runtime evidence. It deliberately sends no chat, changes no camera CVars, and never persists secret values.

## I-001 runtime pass 01

The first probe attempt failed before collecting a snapshot because Forever Lua does not provide `table.pack`. The failure was preserved, diagnosed as a probe compatibility issue, and fixed with a local vararg pack helper.

After `/reload`, the probe recorded runtime snapshots successfully.

The pass established:
- Forever 1.60.1 build 70124 / interface 16001;
- project ID equals MAINLINE;
- player health/power percentages are secret even out of combat;
- secret percentage formatting/text works;
- normalized secret health can drive status-bar value and texture alpha;
- ordinary target level/classification are non-secret in tested world contexts;
- open-world map position/facing works;
- SavedVariables survive `/reload`;
- combat restriction/lockdown state settles after the initial regen-disabled event rather than necessarily being fully updated inside that callback;
- camera and chat-lockdown reads work.

The raw SavedVariables file remains local because it contains session-specific coordinates. A sanitized evidence record was created instead.

Targeted runtime pass 02 remains required for a custom vignette curve, target-in-combat metadata, real cast/channel capture, elite target, instance navigation restriction, quest waypoint, and optional PvP transition.

## I-001 runtime pass 02 and closure

The second runtime file contained 71 snapshots. Instance entry did not reset prior data: 55 world snapshots and 16 party-instance snapshots were preserved in one database, followed by restored world state after instance exit.

The custom Logres health curve succeeded in all 71 snapshots and safely drove secret status-bar value/alpha.

The pass captured:
- active player cast-time and channel states;
- a normal target while combat lockdown was active;
- an elite target during active party-instance combat;
- non-secret target level/classification;
- secret target health/power;
- instance loss of map position/facing;
- restoration of map position/facing after returning to the world.

I-001 was closed with explicit deferrals for phase-owned questions rather than extending the foundation audit indefinitely.

Project next action: Phase 0.3 minimal addon skeleton/load proof.

## Phase 0.3 skeleton prepared

After I-001 closure was pushed at `477df5b`, the first real Logres addon skeleton was prepared.

The skeleton intentionally contains only:
- addon bootstrap/namespace;
- shared event/callback dispatch;
- SavedVariables initialization;
- central world/combat/instance/PvP observation;
- development status/debug commands;
- WSL deployment/static-check tooling.

No product HUD feature was implemented.

The runtime state engine explicitly incorporates the audit finding that combat/restriction state may settle across multiple events rather than assuming `PLAYER_REGEN_DISABLED` is final truth.

Runtime proof remains pending.
