# Logres — Canonical issue and resolution ledger

**Authority:** This is the **first reference for every Logres bug report, investigation, attempted fix, validation, and closure**. Updated 2026-11-05 on the P0373 `2a97a77` baseline. The append-only [issue history](ISSUE_REGISTER.md), original evidence, source, and test transcripts remain authoritative for what actually happened; this ledger is the current status/index, **not a replacement for evidence**.

## Mandatory workflow

1. **Look up the L-ID here before diagnosing a symptom or preparing a patch.** Reuse an existing ID when the symptom/ownership matches; otherwise allocate the next unused `L-xxx` before fixing it. Do not conflate a native fallback, unexpected native overlay, and an unsuccessful native action merely because they all involve the quest UI.
2. On first report, record **date/client build, symptom, expected result, triggering interaction (or unknown), scope, screenshot/Report Bug incident, and evidence path**. Unknown details stay `UNKNOWN`; a user report counts as observed failure, not confirmed root cause. Record severity/native fallback separately in investigation evidence.
3. Record **every attempt and negative outcome** under the same ID in a dated evidence record, including applier refusals, runtime Lua/taint/protected/secret errors, rollback, and unreproduced behavior. The ledger's *Resolution / attempt* column links or summarizes the latest disposition, not just the newest patch.
4. Use `OPEN` for unfixed or causally unknown defects; `PARTIAL` for supported but incomplete behavior; `DEFERRED` for gated work; `BLOCKED` for release constraints. `RESOLVED-SCOPE`, `RESOLVED-DOCS`, and `RESOLVED-TOOLING` require documented evidence appropriate to that scope. A candidate patch, merge/push, static checker PASS, or absence of a repeat **never** constitutes a gameplay resolution.
5. When closing, record **root cause, actual change, patch and verified pushed commit, failed approaches retained, test build/actions, observed PASS, remaining scope, and regression gate** in dated evidence; then change this ledger's status and describe the resolution. When a failure recurs, **REOPEN** the same ID with fresh evidence; never erase the previous PASS.
6. Every bug response and related patch must consult this ledger **first**, link the L-ID, update it with any new status/evidence in the **same checkpoint**, and synchronize `CURRENT.md` only for the active priority. For full narratives follow `ISSUE_REGISTER.md` and the linked evidence. **This is a repository process ledger, not an in-game telemetry or bug-upload feature.**
